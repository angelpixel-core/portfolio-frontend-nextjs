- ADRs enforceable (no solo aspiracionales)
- 0 legacy breakpoints, primitives reutilizables, reglas de contención documentadas

## 3. Qué Nos Costó

### E2E Runtime Diferido (patrón recurrente — 3/7 stories)
- Stories 24.3, 24.5, 24.6 difirieron AC4 (verificación con dev server)
- Acumulación de validación runtime pendiente en epics visual/layout
- **Root cause:** No hay gate session al cierre de epic para runtime validation
- **Mitigación propuesta:** Gate session obligatoria con dev server antes de cerrar epic

### Reviews Adversariales Incompletas (3/7 stories sin review)
- Stories 24.1, 24.2, 24.3 no tuvieron adversarial review
- Story 24.2 (20+ archivos, la más grande del epic) es el gap más preocupante
- Acuerdo de Epic 23 ("review obligatorio") no se aplicó uniformemente
- **Root cause:** No hay threshold que dispare review obligatorio
- **Mitigación propuesta:** Review obligatorio para stories con ≥10 archivos modificados

### Conteos Overestimados (Story 24.4)
- Estimación: 84 legacy usages. Real: 49. Overcount del 41%
- PI-1 de Epic 23 ("conteos verificados con grep") aplicado parcialmente
- Story 24.0 tuvo conteos stale en Dev Notes (atrapados por review M1)
- **Root cause:** Verificación manual insuficiente en fase de estimación

### `@apply` + `@layer utilities` Incompatibility
- Descubierto en runtime en 24.1, impactó 24.2
- `@apply` no resuelve clases de `@layer utilities` en dev mode (Next.js/PostCSS limitation)
- Workaround: CSS nativo inline con comentarios de origen
- **Root cause:** No hubo spike técnico previo
- **Mitigación:** Documentado como regla, no debería repetirse

## 5. Insights Clave

### Principio: "Un Root Cause Fix Vale Más Que 14 Parches"
El mayor logro técnico de Epic 24 fue el cambio `inline-block` → `block` en MainContainer. Un solo fix eliminó toda la cadena de `!important` que propagaba desde el HOC hacia las páginas consumidoras. Esto valida el enfoque de buscar root causes en vez de acumular overrides.

### Contratos Antes de Código
Story 0 (ADRs) transformó el epic de "migración mecánica" a "implementación de contratos". Cada decisión posterior tenía referencia clara. Esto reduce fricción, elimina ambigüedad, y facilita reviews. El patrón se consolida: Story 0 es obligatoria para epics arquitectónicos.

### Constraint Mapping para E2E
Documentar failure modes y constraints ANTES de escribir tests es el equivalente de "ADRs para testing". Evita tests frágiles, elimina falsos positivos, y documenta qué NO se puede testear y por qué. Modelo a replicar.

### Reviews por Riesgo, No por Orden
4/7 stories tuvieron review. Las que no lo tuvieron incluyen 24.2 (la más grande). El criterio debería ser riesgo (archivos modificados, blast radius), no secuencia. Priorizar reviews en stories de alto impacto.

### Narrativa de Consolidación

```
Epic 22 → Type Safety Estructural      → El sistema sabe QUÉ es cada cosa
Epic 23 → Predictibilidad de Imports    → El sistema controla CÓMO se conectan las cosas
Epic 24 → Estabilidad Espacial          → El sistema define DÓNDE van las cosas
```

### Evolución del Criterio de Review: De Pragmatismo a Completitud

A partir de ~Epic 12, el equipo cambió su criterio de abordaje de findings en code reviews. Inicialmente, por velocidad estratégica, se atacaban solo los **High** y se debatían los **Medium**. Con el tiempo, al ver que los findings eran recurrentes y que el proyecto heredado tenía intenciones de buenas prácticas en muchas direcciones (pero todas con deuda no concluida y no documentada), Angel DevStack decidió estirar cada sprint y resolver **todos** los findings — High, Medium y Low.

Esta decisión fue clave: en vez de acumular deuda de review, cada story sale limpia. El costo por sprint es mayor, pero el costo acumulado es significativamente menor. Los 28 findings de Epic 24 (todos resueltos) son evidencia de que el patrón funciona.

No todo quedó resuelto. Es importante documentar con madurez crítica qué se sacrificó y qué sigue siendo tensión activa:

## 5c. Reflexión Estratégica — De Reactivo a Estructural

### Reducción de Entropía Futura

Epic 24 no solo estabiliza el layout actual, sino que **reduce el costo marginal de cualquier nueva feature visual**. El sistema ahora escala mejor:

- Antes: cada feature nueva requería descubrir qué breakpoints usar, cómo contener, dónde aplicar spacing
- Después: ADRs definen contratos, primitives proveen composables, breakpoints son semánticos

**El costo de agregar una feature visual pasó de "investigar + implementar + parchar" a "componer con primitives + validar con E2E".**

### De Portfolio a Sistema Replicable

El proyecto ahora tiene suficiente coherencia arquitectónica como para ser usado como base de otros proyectos:

- Tipado estricto (Epic 22)
- Imports predecibles y protegidos por ESLint (Epic 23)
- Layout system con ADRs, primitives y breakpoints semánticos (Epic 24)
- Testing: 1110 unit + 223 E2E
- Tooling: audit scripts, CI gates, Storybook
- Documentación: 10 ADRs, architecture docs, CLAUDE.md

**Esto cambia la narrativa de "terminamos un portfolio" a "construimos un sistema reusable".**

### Momento de Inflexión Arquitectónica

El sistema dejó de ser reactivo y pasó a ser estructural:

| Antes | Después |
|-------|---------|
| CSS reactivo | Primitives de layout |
| Breakpoints fragmentados | Breakpoints semánticos |
| Layout parcheado | ADRs formales |
| Imports arbitrarios | ESLint-protected |
| Deuda técnica implícita | Deuda técnica explícita |

Esto es madurez de sistema. No es solo orden — es reducción de entropía futura.

## 7. Reflexión del Project Lead — Angel DevStack

### Punto de Inflexión

Epic 24 marca un punto de inflexión en el proyecto.

Ya no estamos iterando sobre parches visuales, sino sobre un sistema espacial definido por reglas explícitas, primitives reutilizables y breakpoints semánticos.

La eliminación de legacy breakpoints y la formalización del layout con Every Layout primitives reducen significativamente la entropía futura del proyecto.

### Tensiones Abiertas

Aún quedan desafíos abiertos:
- Estrategia vertical completamente intrínsica (evitar dependencia en dvh rígido)
- E2E runtime execution real
- Consolidación definitiva del testing strategy
- Reducción progresiva de `!important` heredados

Sin embargo, el sistema hoy es:
- Más predecible
- Más escalable
- Más clonable
- Más mantenible

### Infraestructura, No Features

Epic 24 no entregó features visibles. Entregó infraestructura estructural.

Y eso cambia el costo de todo lo que venga.

### El Momento de Mejorar

El proyecto alcanzó un grado de madurez del cual ya podemos confiar plenamente en lo que resolvimos sobre lo que estaba hecho. Pero ahora la base es nuestra — tenemos más visión, más consenso, y ya no estamos resolviendo cosas sino mejorando.

Estas etapas de mejora casi nunca se dan y es el momento de aprovecharlas. A partir de acá, este se convierte en el modelo para futuros proyectos, cada iteración aumentando la calidad.

Todos participamos de esto. Si lo mejoramos, significa que sabemos acerca de este producto, de esta arquitectura. La hicimos extremadamente agnóstica a propósito: por eso la insistencia en naming consistente, por eso TypeScript para hacerlo lo más arquitectónico posible.

Ahora estamos en el punto prolijo. Es el momento de hacer que la nave tenga nitro.

### Próximo Paso: Auditoría Arquitectónica Profunda

Antes de definir Epic 25, se requiere una **auditoría arquitectónica avanzada de nivel enterprise, profundísima y de altísimo nivel**. No profunda — profundísima.

**Scope de la auditoría:**
- Todos los patrones aplicados — documentación, naming, renombramiento, arquitectura
- Lo que se recomienda ignorar vs lo que se recomienda cambiar
- Cosas no del todo bien arquitectadas o diseñadas
- Investigación exhaustiva de patrones adicionales (funcionales, estructurales, de testing)
- Listado exhaustivo de todo lo mejorable para poder ordenar, agrupar por zona, debatir y planificar

**Objetivo:** No es solo "qué falta", sino "qué podemos hacer mejor ahora que tenemos la base limpia".
