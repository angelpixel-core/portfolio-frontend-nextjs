## 🧭 Decisiones de Alcance y Cierre

Durante Epic 4 se priorizó cerrar historias cuando los criterios funcionales y no funcionales estaban cumplidos, incluso cuando se detectaron oportunidades de mejora adicionales.

**Se decidió documentar deuda técnica MEDIUM y LOW en lugar de resolverla inmediatamente**, para evitar scope creep y mantener el foco del epic en descubrimiento de contenido y SEO.

### Ejemplos concretos:

| Decisión | Por qué fue correcta |
|----------|---------------------|
| No unificar `params` typing entre articles/projects | Next 14 acepta ambos; no rompe funcionalidad; refactor cosmético |
| No extraer author a config central | Requiere decisión de ownership más amplia; no bloquea SEO |
| Documentar `renderJsonLdScript` unused | Puede ser útil en futuro; eliminar ahora es prematuro |
| Tests de sitemap/robots marcados out-of-scope | Validación manual suficiente; tests E2E corresponden a Epic 6 |

**Insight:** Saber cuándo NO tocar algo también es una decisión técnica. El criterio fue: "¿Rompe AC? ¿Rompe contrato? Si no, documenta y sigue."

## 🔍 Validación Manual como Práctica Explícita

Dado que varios objetivos del epic (SEO, SSR, indexabilidad) no pueden validarse completamente con tests automatizados, se incorporó una **validación manual explícita** como parte del Definition of Done.

### Qué se validó manualmente:

- Inspección directa del HTML renderizado (View Source)
- Verificación de `<meta>` tags (title, description, og:*)
- JSON-LD visible en page source
- Sitemap.xml y robots.txt generados post-build
- Canonical URLs resueltas correctamente
- Comportamiento SSR desde perspectiva de crawlers

**Por qué importa:** Los tests automatizados verifican que el código genera las estructuras correctas, pero no pueden verificar que Google realmente indexará el contenido. La validación manual cierra ese gap.

---

## 🧠 Lecciones Aprendidas

### Técnica

> Next.js Metadata API funciona correctamente para SSR y SEO, pero requiere atención especial en **páginas de listado** y **componentes client-side** para evitar gaps de indexabilidad.

El code review de Story 4.4 detectó que `/articles` y `/projects` (Client Components) no tenían metadata. La solución fue agregar metadata en los layouts existentes, no convertir las páginas a Server Components.

### Proceso

> El mayor desafío no fue técnico sino **decidir cuándo parar**. Documentar explícitamente deuda técnica permitió cerrar historias con confianza sin comprometer la calidad global.

El criterio "HIGH → fix, MEDIUM/LOW → document" funcionó bien. Evitó debates infinitos y mantuvo momentum.

## 🔁 Qué Ajustaríamos en Epic 5

Para futuros epics con foco en **integraciones externas** (Calendly, WhatsApp, Chat):

1. **Definir desde el inicio qué validaciones serán manuales y cuáles automatizadas**, para reducir ambigüedad al momento del cierre.

2. **Documentar mocks de servicios externos temprano** - Epic 4 trabajó con datos locales; Epic 5 tendrá dependencias reales.

3. **Considerar feature flags** si hay integraciones que pueden fallar en producción (Calendly embed, WhatsApp links).
