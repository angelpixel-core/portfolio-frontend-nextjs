## Qué Aprendimos (LEARN)

### 1. Cerrar sin Eliminar Todo es Decisión Consciente

> "Cerrar una épica sin eliminar todos los warnings es una decisión consciente, no un fallo."

**Aprendizajes clave:**
- No todo warning es deuda crítica
- La ausencia de critical issues es señal clara de DONE
- La retro es el lugar correcto para mover trabajo al futuro, no el code review
- Documentar deuda ≠ postergar indefinidamente

### 2. Separación Clara de Concerns

Issues identificados que NO fueron scope de Epic 9:
- Hydration warnings (runtime)
- Preload warnings (performance)
- UX responsive pendiente (features)

> **Aprendizaje de proceso:** Separar deuda técnica de nuevos requerimientos evita reabrir épicas innecesariamente.

### 3. Precisión sobre Vaguedad

Story 9.3 estableció un estándar importante:
- "Many" → 43 bloques de código
- Metodología documentada para auditorías futuras
- Métricas verificables y repetibles

## Qué Podemos Mejorar (IMPROVE)

### 1. Carriles Explícitos para Tipos de Trabajo

**Propuesta:** Formalizar épicas separadas para:
- Documentación (Epic 9 ✅)
- Infraestructura/Tests (Epic 7-8 ✅)
- Runtime/Client-side stability (futuro)
- UX nueva (futuro)

**Beneficio:** No mezclar concerns diferentes en una misma épica.

### 2. Usar Retros para Crear Próximas Épicas

Las retrospectivas deben ser input explícito para definir próximas épicas, no para extender la actual.
