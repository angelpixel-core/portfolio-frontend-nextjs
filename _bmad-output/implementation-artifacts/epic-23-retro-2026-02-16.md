## 3. Qué Nos Costó

### Conteos Aproximados (Patrón recurrente — 3/4 stories)
- Story 23.2: exports contados imprecisamente
- Story 23.3: Dev Notes decían "~55" y "~35" en vez de 52 y 44
- Story 23.4: Audit script reportaba state=8 (real: 52), organisms=15 (real: 20)

### Bug H1: Parser Multi-Line (Story 23.4)
- `audit-barrels.ts` no manejaba `export { A, B, C } from "..."` en múltiples líneas
- Primera corrección falló (double-counting con dos regex overlapping)
- Segunda corrección exitosa: "collapse then parse" — colapsar multi-line a single-line antes de parsear
- **Mitigación que funcionó:** Adversarial code review lo detectó antes de producción

### Documentación Stale

- `.js` → `.ts` no actualizado después de Epic 22

## 5. Insights Clave

### Principio: "El Sistema Se Protege Solo"
El mayor logro de Epic 23 no es haber limpiado barrels. Es que ahora el sistema **previene** que vuelvan. ESLint bloquea imports prohibidos, el audit script detecta candidates, los deprecation warnings guían a developers. Esto es madurez de ingeniería.

### Consolidación → Replicabilidad
El proyecto dejó de ser "un portfolio" y empezó a ser una base reutilizable:
- Arquitectura tipada consistente (Epic 22)
- Reglas de import claras y enforceables (Epic 23)
- Estructura modular con convenciones documentadas
- Tests sólidos + tooling defensivo

Esto permite clonar y adaptar para: portfolio profesional, vitrina de proyectos, sitio de profesional independiente, o sitio corporativo pequeño.

### El Bug como Test del Sistema
El bug H1 del audit script no fue un fallo del equipo — fue un test del proceso. Y el proceso respondió: adversarial review → detección → corrección → verificación. Eso valida que las capas de protección (lint, typecheck, tests, review) funcionan.

### Articles como Blog Interno (Candidate for Exploration)
La sección Articles funciona conceptualmente como blog técnico embebido. La infraestructura ya existe (domain layer, React Query, Zod, SSG). Decisión estratégica pendiente: mantener contenido interno (control SEO, coherencia visual, consolidar autoridad en un dominio) vs externalizar (Medium, Blogspot). **Se evalúa post-Epic 24.**

## 6. Descubrimiento Significativo: Redefinición de Epic 24

### El Problema Real
Epic 24 estaba planificado como "Breakpoint Migration + Every Layout" — esencialmente reemplazar breakpoints legacy por semánticos.

La retrospectiva reveló que el problema real es más profundo:
- El sistema responde en ancho pero **no tiene reglas de contención vertical**
- Componentes definen espacio que debería ser responsabilidad del layout contenedor
- No hay spacing scale definida, ni max-width policy, ni min-height strategy
- `position:absolute` frágiles, z-index sin sistema, overflow inconsistente

### El Reframe
**Epic 24 no es una migración de breakpoints. Es la definición del sistema espacial del proyecto.**

Tres niveles a separar:
1. **Layout** — flujo, stacking, distribución, límites, contención, relación espacial
2. **Componente** — identidad visual, comportamiento, variaciones, estados
3. **Reglas de composición** — cómo componentes se relacionan dentro de layouts

### Estructura Revisada

**Nombre:** Epic 24 — Spatial System & Layout Stabilization

```
Story 0  — Spatial System Definition (ADRs, audit, contratos)
           NO se toca código productivo
           Extensible: 0-A, 0-B, 0-C si el scope se abre
Story 1  — Implement Layout Primitives (globals.css)
Story 2  — Migrate Page by Page
Story 3  — Vertical Viewport E2E Tests
Story 4  — Breakpoint Normalization (legacy → semantic)
Story 5  — CLS Validation & Stabilization
```

### Story 0 — Deliverables Requeridos

1. **ADR: Spacing Scale** — Base unit (4px/8px), scale progression, gap rules, vertical rhythm
2. **ADR: Containment Rules** — max-width por nivel, min-height strategy, overflow behavior, blade definition
3. **ADR: Layout vs Component Responsibilities** — qué propiedades pertenecen a cada capa, prohibiciones explícitas, reglas de composición
4. **Layout Audit Document** — width hardcodeados, absolute positioning frágil, z-index inconsistentes, ausencia de min-height

**Definition of Done de Story 0:** ADRs versionados en `/docs/adr`, tabla de espaciado, lista de anti-patterns, aprobación explícita. CERO código productivo.

### Impacto
**Epic update required:** La definición actual en `epics-v4.md` necesita reflejar esta nueva estructura antes de crear stories.
