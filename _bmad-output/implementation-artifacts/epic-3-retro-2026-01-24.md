# Epic 3 – Retrospective

**Epic:** Historia Profesional
**Estado:** DONE
**Duración:** 4 stories (3.1 → 3.4)
**Fecha:** 2026-01-24

---

## 1. Qué salió bien (y por qué es importante)

### Flujo de desarrollo estable
- Branching por story respetado
- Commits atómicos y legibles
- Merges limpios hacia la epic
- `main` quedó como resultado final, no como espacio de trabajo

**Insight:**
El proceso dejó de ser una carga cognitiva y pasó a ser "infraestructura invisible". Eso es señal de madurez del flujo.

---

### TDD pragmático funcionó
- Tests escritos antes o en paralelo al feature
- Tests como red de seguridad real (no decorativos)
- Confianza alta para refactors (ej. schema académico)

**Insight:**
No fue TDD dogmático, fue TDD orientado a intención, lo cual permitió avanzar sin frenar.

---

### Accesibilidad tratada como parte del dominio
- `prefers-reduced-motion`
- Foco visible
- a11y tests reales (axe, keyboard)
- Empty states accesibles

**Insight:**
La accesibilidad no apareció como "fix tardío", sino como criterio de diseño desde el inicio.

---

## 2. Qué no salió perfecto (pero estuvo bien detectado)

### Deuda visual / UX deliberadamente aceptada

**Ejemplos:**
- Progress line del timeline cargada completamente desde el inicio
- Trigger "Show / Hide details" explícito en lugar de affordance implícito

**Decisión consciente:**
No se corrigió porque:
- No rompe ACs
- No está especificado con precisión
- Corresponde a una fase de polish visual

**Aprendizaje:**
Saber cuándo NO tocar algo también es una decisión técnica.

---

### Warnings de hydration (SSR/CSR)
- No rompen funcionalidad
- No afectan UX visible
- Aparecen por mocks + framer-motion

**Decisión:**
Documentado como deuda técnica transversal, no resuelto dentro de la story.

---

## 3. Decisiones importantes tomadas durante el epic

### Sobre fixing issues

Se aplicó el criterio:
- **HIGH / MEDIUM** que rompen contrato → se fixean
- **LOW** → se documentan

**Ejemplo claro en Story 3.4:**
- ✔️ CSS y focus states → fix
- ✔️ Campo `type` no usado → removido
- ❌ mock URL / aria-label redundante → documentados

**Insight:**
Esto evitó scope creep sin sacrificar calidad.

---

### Sobre datos y backend
- Se trabajó con domain data real (seed) sin endpoints
- Frontend definió contratos TS
- API quedó explícitamente como "pending"

**Insight:**
Esto permitió avanzar sin bloquearse por infraestructura inexistente.

---

## 4. Qué aprendimos (lo más valioso)

### Aprendizaje técnico
- Versionar artefactos de tracking (BMAD) implica conflictos previsibles
- Esos conflictos no son errores, son parte del diseño
- **Regla clara:** en merge story → epic, el estado DONE de la story gana

---

### Aprendizaje de proceso (clave)

> **El mayor riesgo no fue técnico, sino decidir cuándo parar.**

El sistema empezó a fluir cuando:
- Dejamos de buscar "dejarlo perfecto"
- Y empezamos a cerrar con criterio explícito

**Esto es totalmente transferible a proyectos reales.**
