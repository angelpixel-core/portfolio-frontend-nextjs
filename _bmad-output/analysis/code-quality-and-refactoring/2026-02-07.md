Objetivo: Auditoría integral de calidad técnica post-épica

Contexto

Acabamos de cerrar una épica mayor del proyecto portfolio-frontend-nextjs.
La épica introdujo cambios significativos en:
• Arquitectura de UI
• Definición de UX y layout
• Organización de componentes
• Estado, navegación y overlays
• Tests (algunos heredados, otros adaptados)

Todos los tests actualmente pasan, y la épica se considera cerrada.
No buscamos reabrirla ni hacer fixes reactivos.

El objetivo ahora es re-analizar el estado actual del codebase con una mirada fría, estructural y estratégica.

⸻

🧠 Rol esperado

Actuás como BMAD – Technical / Product Analyst, no como developer ejecutor.

No debés:
• Escribir código
• Proponer fixes inmediatos
• Reabrir decisiones ya cerradas

Sí debés:
• Analizar
• Clasificar
• Priorizar
• Recomendar próximos pasos

⸻

📦 Alcance del análisis

Analizá todo el codebase actual según los siguientes ejes:

1. Calidad de Código
   • Complejidad accidental
   • Claridad de responsabilidades
   • Acoplamiento innecesario
   • Legibilidad y consistencia

2. Refactorización
   • Oportunidades claras de refactor
   • Refactors estructurales vs cosméticos
   • Riesgo estimado por refactor
   • ROI técnico (bajo / medio / alto)

3. Reutilización y Modularización
   • Componentes duplicados o casi duplicados
   • Hooks repetidos
   • Lógica que debería extraerse a capas comunes
   • Barrel files y organización de exports

4. Eliminación de Duplicados
   • CSS duplicado
   • Lógica duplicada
   • Queries, helpers o utilidades redundantes

5. Tests
   • Cobertura real vs cobertura ilusoria
   • Tests frágiles vs tests de contrato
   • Tests que testean implementación interna
   • Tests que aportan valor vs ruido
   • Deuda de testing (si existe)

6. Arquitectura General
   • Coherencia entre domains, UI y state
   • Separación de responsabilidades
   • Flujo de datos claro o difuso
   • Dependencias implícitas

7. Documentación
   • Documentación existente útil
   • Documentación faltante crítica
   • Documentación obsoleta
   • Qué conviene documentar ahora y qué no

⸻

📊 Entregables esperados

1️⃣ Informe de Estado Actual

Un resumen claro del estado del proyecto hoy, por ejemplo:
• “Arquitectura sólida con deuda puntual”
• “Buena base, pero con ruido acumulado”
• “Lista para escalar / no lista para escalar (y por qué)”

⸻

2️⃣ Mapa de Deuda Técnica

Clasificá cada ítem detectado como:
• 🔴 Crítica (bloquea evolución)
• 🟡 Media (conviene atacar)
• 🟢 Baja (puede esperar)

Para cada uno:
• Descripción clara
• Área afectada
• Impacto
• Riesgo
• Urgencia

⸻

3️⃣ Recomendaciones Estratégicas

No más de:
• 5–7 refactors prioritarios
• 3–5 mejoras de testing
• 3–5 mejoras estructurales

Evitar listas infinitas.

⸻

4️⃣ Propuesta de Roadmap Técnico

Sugerí cómo continuar el trabajo, por ejemplo:
• ¿Nueva épica de refactor?
• ¿Hardening sprint?
• ¿Auditoría de seguridad / performance?
• ¿Congelar y pasar a features?

Indicá orden recomendado, no solo opciones.

⸻

5️⃣ Actualización del “Cloudy Index” (si aplica)

Si el proyecto utiliza un índice interno de calidad (Cloudy u otro):
• Re-evaluar el score actual
• Justificar subidas o bajadas
• Explicar qué acciones mejorarían el índice

⸻

🚫 Fuera de alcance explícito

No hacer:
• Fixes tácticos
• Cambios de naming menores
• Ajustes cosméticos
• Rewrites grandes

Este análisis no es para ejecutar, es para decidir.

⸻

🧩 Tono y estilo esperado
• Técnico pero claro
• Sin dogma
• Sin “best practices” genéricas
• Basado en este proyecto, no en proyectos ideales

⸻

✅ Resultado esperado

Al finalizar, deberíamos poder responder con claridad:

“Este es el estado real del proyecto hoy, esta es la deuda que vale la pena pagar, y este es el camino lógico para seguir.”
